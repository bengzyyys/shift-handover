# 本地班次交接与未关闭事项

在本机运行的本地班次交接与未关闭事项管理工具。数据持久化在本地 JSON 文件中，
**退出后重新打开，数据与处理进度仍在**；写入采用临时文件 + 原子改名，业务校验失败或
写盘失败都会回滚，失败前已保存的数据保持不变。

## 构建与测试

```bash
go build ./...
go test ./...
go run ./cmd/handover help
```

## 数据文件

默认使用当前目录 `handover-data.json`，可用全局参数 `--data /路径/文件.json` 或环境变量
`HANDOVER_DATA` 指定。时间一律使用带时区偏移的 RFC3339，例如
`2026-10-02T08:00:00+08:00`。

## 命令一览

```bash
# 班次
handover shift-add   --position 岗位 --owner 负责人 --start 开始 --end 结束 [--note 重叠说明]
handover shift-list
handover shift-close --id S001
handover shift-show  --id S001      # 按班次查询完整报告

# 重叠说明（重叠建立班次时必填说明，也可事后追加）
handover note-add  --a S001 --b S003 --note "抢修并行一小时"
handover note-list --id S001

# 事项
handover item-add    --shift S001 --content 内容 --severity normal|important|urgent \
                     [--constraints 限制条件] --follow 后续负责人
handover item-update --id I001 --content 内容 --severity normal|important|urgent \
                     [--constraints 限制条件] --follow 后续负责人
handover item-close  --id I001 --operator 操作人
handover item-show   --id I001      # 凭事项编号查看最新状态与从建立到当前的完整处理经过

# 交接
handover handover-create   --from S001 --to S002
handover handover-list
handover handover-show     --id H001
handover handover-process  --id H001 --item I001 --action confirm|return|track \
                           --operator 操作人 [--reason 退回原因] \
                           [--note 跟踪说明 --follow 后续负责人]
handover handover-resubmit --id H001 --item I001 --operator 操作人 --supplement 补充说明
```

严重程度与操作同时接受英文标识和中文（普通/重要/紧急，确认接收/退回/继续跟踪）。

## 业务规则

- **班次**：岗位、负责人、带时区起止时间必填，结束必须晚于开始；编号稳定（S001…）。
  同一岗位按实际时刻比较区间，前班结束恰好等于后班开始不算重叠；重叠时必须填写说明，
  说明与涉及的班次可查询。不同岗位互不影响。
- **事项**：仅未结束班次可新增；内容、严重程度（普通/重要/紧急）、后续负责人必填，
  限制条件可空；编号稳定（I001…），结束前可修改、关闭。班次结束后，未关闭事项成为
  待交接清单，已关闭事项保留；已结束班次的事项内容与当时关闭状态不可改、不可删。
  空清单也能结束班次。
- **结束时记录**：班次成功结束时，把当时在班的全部事项（本班新增与已经接收的事项，
  含结束前已关闭者）冻结为结束时记录：内容、严重程度、限制条件、后续负责人、关闭
  人和关闭时间均以结束时刻为准，之后后班的修改、关闭与交接都不改变该记录。
  `shift-show` 查看已结束班次时事项区明确标为结束时记录，并另外列出每项的当前所在
  班次、最新负责人与最新关闭情况，与结束时信息对照；结束时未关闭的事项不会因后班
  关闭而显示成当时已关闭。空清单结束后显示“结束时没有事项”。结束失败（校验或保存
  失败）不留下记录，班次保持进行中，重试成功以那次成功时为准；重复结束已结束班次
  报错。旧数据中缺少结束时记录的已结束班次，事项区标为“历史记录不完整，以下为当前
  信息”，不把当前值宣称为结束时事实；旧的进行中班次成功结束后仍会留下完整记录。
  `item-show` 继续展示事项最新状态与完整处理经过（含各次交接的退回与补充）。
- **发起交接**：交给同岗位、尚未结束且开始时间不早于交班开始的班次；不能交给自身或
  其他岗位；区间重叠但已有说明时允许。一个交班班次只能指定一个接班对象——重复发起
  返回已有记录且不复制事项，改换对象报错。重复发起在接班班次结束后仍然成立：用原交班、
  接班编号再次执行 `handover-create` 一律视为成功并展示原交接记录，沿用原交接编号、
  两班关系、发起时间与完成时间，以及各事项当时的确认接收/继续跟踪结果、处理人、处理
  时间和历次退回与补充经过；事项后来在接班班次关闭或继续流转到下一班都不改变返回内容
  （仍展示原交接的清单与结果，不按事项最新所在班次重新挑选），发起时即完成的空清单
  交接也返回原记录与原完成时间。重复返回不重新接收事项、不追加处理经过、不移动事项、
  不改变班次结束时记录，后续班次已有的交接也不受影响。已经有交接记录时改用另一个确实
  存在的班次作为接班对象，无论该班次是否结束都明确拒绝改换并指出原来指定的接班班次，
  不生成第二条交接；首次发起仍要求交班班次已经结束、接班班次尚未结束。输入不存在的
  班次编号仍明确报错，不用已有记录掩盖编号错误。
- **逐项处理**：确认接收 / 退回（必填原因）/ 继续跟踪（视为已接收，必填跟踪说明与
  后续负责人），每次处理必填操作人。交接完成以清单里每一项都明确为确认接收或继续
  跟踪为准：待处理、退回，以及旧数据中处理结果缺失（空）或不属于四种结果的记录，
  都使交接保持未完成，其他项全部已接收也不能抵消不确定项，即使记录里已有交接完成
  时间也不掩盖；空清单直接完成。完成时间记录这份交接真正接收齐全部事项的时刻：
  最后一项成功接收（确认接收或继续跟踪）时以该次成功处理的时间为准；旧记录若在仍有
  结果缺失、无法识别、待处理或退回项时误写过完成时间（或只留下零值时间），接班人
  逐项补齐、最后一项成功接收后，用这次处理时间覆盖旧时间，不沿用补齐前的时刻。
  退回、补充后重新提交、单纯查询与重复发起都不更新完成时间；最后一次处理因缺少必填
  信息而失败时该项保持原结果，交接不能提前完成；也不为已经全部接收但缺少完成时间的
  旧记录编造时刻（展示为未记录）。查看交接清单时，缺失或空结果显示“处理结果未记录”，
  无法识别的结果显示“处理结果无法识别”并带出保存的原值，不从事项所在班次、处理人、
  处理时间或退回历史推测接收结果。已接收项不能再次退回。**退回表示等待交班人补充**：
  退回后、交班人尚未在原交接记录上补充并重新提交前，接班人不能直接确认接收、继续
  跟踪或再次退回同一项——即使填写了操作人、退回原因或跟踪说明也报状态错误，提示先
  补充说明并重新提交；失败后该项仍为退回，不增加退回轮次、不覆盖上次处理人和时间、
  不调整后续负责人、不移动事项所在班次，交接完成情况也不变。
- **退回与重新提交**：交班人在原交接记录上对退回项追加非空补充说明（纯空格视为空）
  并重新提交，不另建交接记录或复制事项。补充写入最近一次退回记录，保留这一轮的原因、
  退回人和退回时间，并记录补充人、补充时间与重新提交时间；以前各轮的说明不覆盖。
  成功后仅这一个事项恢复待处理，当前结果中的接班处理人和处理时间显示为尚未处理，原来
  的退回处理信息仍可从退回历史查看。重新提交本身不表示接收，事项仍留在交班班次，原文、
  严重程度和限制条件不变，同一交接中的其他事项不受影响。对待处理、已确认或继续跟踪的
  事项重新提交报状态错误，不写入补充说明。重新提交后接班人按原规则确认、继续跟踪或
  再次退回；再次退回才产生下一轮记录并重新等待补充，此前某轮已有补充不能代替新一轮的
  重新提交。确认和继续跟踪仍只接收一次，保留事项编号与流转历史。
- **流转**：确认与继续跟踪的事项进入接班班次未关闭清单，可在该班结束前关闭，否则随
  该班再次交接，始终保留原事项编号与此前历史。接班班次收到的任一交接仍存在未确认
  接收的事项（待处理、退回、结果缺失或无法识别）时不能结束，其他交接已完成也不能
  放行；结束失败不改变交接结果、事项归属与已保存的处理经过。
- **查询**：`item-show` 凭一个事项编号展示最新内容、严重程度、限制条件、后续负责人、
  当前所在班次、关闭情况和流经班次，并给出从建立到当前的完整处理经过：保留创建、
  修改与关闭记录，并加入该事项参与的各次交接（发起、逐轮退回、补充后重新提交、
  确认接收或继续跟踪），跨多个班次也无须先知道交接编号。经过按实际发生时刻排序
  （不同时区按同一实际时刻比较），同一时刻下同一交接内保持发起、退回、重新提交、
  后续处理的先后，不同交接按编号排列；同一次接收只展示一次——交接清单中的确认接收
  或继续跟踪与事项自身保存的接收历史合并时，除操作人与实际时刻相同外，还要接收说明
  中明确记载的交接编号、交班、接班班次与接收方式都一致；明确记载的接班班次或接收方式
  不同（如同一时刻由同一人记录的、交给另一个班次的历史接收说明）则各自保留，说明缺少
  足够信息（旧数据或没有对应交接清单的接收历史）时同样原样保留，不凭班次负责人、事项
  当前位置或当前处理结果猜测归属，也不凭空补交接编号；两条历史的存放先后不影响结果。
  合并后的接收记录带出交接编号、交班和接班班次，以及该次保存的处理结果、操作人和时间，
  继续跟踪还保留当时的跟踪说明与后续负责人；事项后来修改的负责人只在开头最新状态展示，
  不替换当时的记录。发起交接未记录操作人
  时明确显示未记录，不以班次负责人代替；旧数据缺少的人名或时间同样标为未记录。
  查询同时列出该事项在每次交接中的当前处理结果：退回未重新提交显示等待交班人补充，
  重新提交后显示待处理、接班人尚未处理；尚未参与交接的事项显示暂无交接记录。
  当前保存的结果是退回、却没有任何退回轮次记录的旧数据，处理经过仍呈现这次已经
  发生的退回（带出原交接编号、交班与接班班次，处理人与处理时间各自使用该项当前
  保存的信息，缺姓名或缺时间分别标为未记录，处理时间缺失或为零值时排在有真实
  时间的经过之后，不拿交接发起时间补齐），并明确提示“退回历史不完整”、退回原因
  未记录；不编造第几次退回、补充说明或重新提交经过。已有退回轮次的事项仍展示
  逐轮退回与补充经过，不因当前结果仍为退回再增加一条相同记录；待处理、确认接收、
  继续跟踪、结果缺失或无法识别时，不凭残留的处理人或时间认定发生退回。查询不
  写入退回轮次、不改变事项归属、交接完成情况或班次结束时记录。
  `shift-show` 对已结束班次展示结束时冻结的事项记录（内容、严重程度、
  限制条件、后续负责人、关闭人与关闭时间），并对照每项最新状态；进行中的班次展示
  当前事项；另展示接班对象、每项当前结果，以及操作人、处理时间和历次退回与补充
  说明。事项的关闭信息在 `item-show` 最新状态与 `shift-show` 当前事项、结束时记录、
  最新状态对照中按同一条规则展示：保存的关闭状态为已关闭即显示已关闭，不因关闭人或
  关闭时间缺失改成未关闭；关闭人未保存或为空显示未记录，关闭时间未保存、为 null 或为
  0001-01-01T00:00:00Z 同样显示未记录，姓名与时间分别判断，有姓名无时间保留姓名并指出
  时间未记录，有真实时间无姓名保留带时区的实际时间并指出关闭人未记录，二者都有沿用
  原格式，不以班次负责人或处理经过补齐。结束时记录的缺项只在结束时信息中标出，不从事项
  最新值或处理经过补齐；结束时未关闭、后班才关闭的事项原班仍显示结束时未关闭，最新状态
  对照显示当前关闭信息（含缺项）；没有结束时记录的旧班次仍只给历史不完整提示并展示当前
  关闭情况，不把当前值当成结束时记录。保存状态为未关闭时，即使残留关闭人或时间也按未关闭
  展示；查询只读，不补写关闭人或关闭时间。`handover-show` 与 `shift-show` 中单项“最后处理”和“各项交接当前结果”
  均以已保存的处理结果区分是否处理过：确认接收、继续跟踪、退回都算已处理，有处理人
  显示原姓名、缺失显示未记录，有真实处理时间沿用带时区展示，时间缺失或为
  0001-01-01T00:00:00Z 时显示未记录；姓名与时间分别展示，缺一个不隐藏另一个，
  不以班次负责人、交接发起时间或退回历史中的时间代替。真正待处理（含退回后已补充
  重新提交、等待接班人再次处理）才显示尚未处理，上一轮退回人和时间留在退回历史中，
  不作为本次当前处理信息。报告嵌入的交接清单与末尾结果说明一致，交班、接班两个视角
  事实相同。不存在的编号、缺少必填信息、不允许的状态操作都返回明确错误。

## 代码结构

```
handover/            领域模型、业务规则、JSON 原子持久化与展示
  model.go           班次/事项/交接/重叠说明等结构
  errors.go          领域错误
  store.go           本地 JSON 存储（快照回滚 + 原子写盘）
  service.go         全部业务规则
  journey.go         item-show 查询结果的组装（退回轮次展开、经过排列、各次交接当前结果整理）
  received_merge.go  item-show 中事项接收历史与交接清单接收记录的合并判定
  render.go          中文命令行展示
cmd/handover/        命令行入口
```
